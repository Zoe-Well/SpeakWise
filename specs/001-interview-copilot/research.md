# Phase 0 研究与技术决策 (Research)：智能面试助手

**功能**：[spec.md](./spec.md) ｜ **计划**：[plan.md](./plan.md) ｜ **日期**：2026-07-10

本文件汇总实现阶段的关键技术决策，解决计划中的全部待定项。每项遵循「决策 / 理由 / 备选方案」格式。

## 0. 运行环境与版本基线

- **决策**：后端锁定 **Python 3.12**（`>=3.12,<3.13`）；配套依赖版本对齐 Python 3.12 的稳定生态：
  - 后端：FastAPI 0.115.x · Uvicorn[standard] 0.32.x · Pydantic 2.9.x · SQLModel 0.0.22（SQLAlchemy 2.0.x）· httpx 0.27.x · sse-starlette 2.1.x · python-multipart · openai 1.x（DeepSeek OpenAI 兼容客户端）
  - 测试：pytest 8.3.x · pytest-asyncio 0.24.x
  - 前端/桌面：Node.js 20 LTS · Electron 32.x · electron-builder 25.x · React 18.3 · Vite 5.x · TypeScript 5.5 · Tailwind CSS 3.4 · shadcn/ui（Radix + lucide-react）· TanStack Query 5.x
- **理由**：用户指定使用 Python 3.12。相较更激进的 3.14，3.12 生态成熟、上述关键库均有稳定 wheel 与长期支持，降低依赖兼容风险；固定次版本区间（`<3.13`）避免隐式跨大版本升级。
- **备选方案**：Python 3.14（生态尚新、部分库支持滞后）——按用户要求放弃；Python 3.11（可行但用户明确选 3.12）——未选。

## 1. 交付形态与整体架构

- **决策**：Electron 桌面壳 + React（Vite + TypeScript + Tailwind CSS + shadcn/ui）前端 + 本地 Python/FastAPI 后端。Electron 主进程启动时拉起 FastAPI 子进程，前端经本地回环地址（`127.0.0.1`）调用后端，流式生成经 SSE 传输。
- **理由**：用户显式指定该技术栈；桌面形态契合"单用户、私有化、本地数据"的定位；shadcn/ui + Tailwind 可快速搭出简历表单 + Chat 界面；FastAPI 原生支持异步与 SSE 流式，适配打字机效果。
- **备选方案**：
  - Streamlit 单体（最快，但定制交互与打包为桌面应用较弱）——用户未选。
  - 纯 Web（浏览器）部署——与"本地私有化桌面工具"定位不符。

## 2. LLM 模型路由

- **决策**：**单一模型全流程**——JD 解析与话术生成均使用 **DeepSeek-V4-Pro**。后端设 `llm/` 抽象层（统一的 `chat`/`stream` 接口 + 结构化输出解析），模型可配置替换。
- **理由**：用户选择"单一模型全流程"，减少一套 API 凭证与路由复杂度；DeepSeek-V4-Pro 兼具高性价比生成与足够的解析推理能力；抽象层保证未来可切换或引入多模型而不改动业务代码。
- **参数建议**：生成温度 0.3–0.5（兼顾事实一致与自然流利，满足 SC-006 可复现性）；JD 解析走结构化输出（JSON schema）以稳定字段。
- **备选方案**：Claude 解析 + DeepSeek 生成的双模型路由（myspec 原方案）——用户为简化实现而放弃；抽象层保留未来回归该方案的可能。

## 3. 数据存储

- **决策**：**本地 SQLite** 作为结构化数据的唯一真源，数据库文件 `data/copilot.db`；JD 原文缓存为 `data/jd_cache/*.txt`。经 SQLModel/SQLAlchemy 访问，启动时自动建表/迁移。
- **理由**：用户选定 SQLite；单文件零配置、便于备份与手改；结构化关系（Profile↔经历↔技能）用关系表建模清晰，支持多份经历的增删改查。
- **备选方案**：本地 JSON 文件（更直观但查询/一致性弱）——未选；直接用 PostgreSQL 作主库（对本地桌面过重）——未选。

## 4. RAG / 向量检索（Pgvector）

- **决策**：**MVP 不启用**。MVP 阶段将完整 Profile + JD 直接注入 128k+ 上下文。Pgvector（PostgreSQL + pgvector 扩展）作为**可选后续增强**，仅当用户历史/上下文超出上下文窗口时启用，用于对经历片段做语义检索后再注入。预留 `backend/src/services/retrieval` 与 `db/` 扩展位。
- **理由**：与 myspec"向量检索（可选）"一致；避免在本地桌面应用初期即引入 PostgreSQL 服务的部署与运维开销；解决了"本地 SQLite（真源）"与"Pgvector（语义索引）"的职责划分——两者不竞争，Pgvector 为可从 SQLite 重建的派生索引。
- **待用户确认的取舍**：若坚持 MVP 即启用 pgvector，需引入本地/容器化 PostgreSQL（或改用 `sqlite-vec` 等嵌入式方案）；本计划默认延后，用户如需前置可提出调整。
- **备选方案**：`sqlite-vec`/`chromadb` 等嵌入式向量库（免 Postgres，但用户点名 pgvector）——作为若需前置时的轻量替代记录在案。

## 5. 分层 Prompt 工程与版本管理

- **决策**：在 `backend/src/prompts/` 建立分层、可版本化的 Prompt 模板体系，对应 myspec 的三层结构：
  - `SYSTEM_ROLE`（不可变角色定义：资深面试教练，基于事实、擅长叙事包装）
  - `USER_CONTROL`（硬规则：由前端开关/文本框控制的结构与策略指令）
  - `DYNAMIC_CONTEXT`（系统注入：`resume_json` / `jd_analysis` / `user_question`）
  以纯模板 + 版本号（如 `self_intro_v1`）管理，不引入重量级框架。
- **理由**：满足 FR-014（硬规则）/ FR-015（软自适应）双轨控制；纯模板便于测试与固化"硬规则"，避免 LangChain 等框架的额外抽象与依赖；版本号支持 Prompt 迭代与回溯。
- **备选方案**：LangChain（myspec 提及"LangChain 风格"）——仅取其"分层"思想，不引入库以保持轻量。

## 6. 流式输出（打字机效果）

- **决策**：FastAPI 侧用 `sse-starlette` 以 Server-Sent Events 流式推送模型增量 token；前端用 `EventSource`/fetch-stream 逐段渲染。
- **理由**：满足 FR-017 与 SC-004（首字 < 2s）；SSE 较 WebSocket 更轻，单向流式足够；与 React 状态更新配合实现打字机效果。
- **备选方案**：WebSocket（双向，但本场景无需）；一次性返回（不满足流式体验）。

## 7. 自我介绍结构与长度控制

- **决策**：自我介绍固定三段式（概述 → 技能+证据 → 业务匹配），由 Prompt 硬规则约束；生成后做**长度后校验**（约 300–400 字），超出/不足时提示或触发再生成/裁剪。
- **理由**：满足 FR-007 / FR-010 / SC-001 / SC-005；结构由 Prompt 保证、长度由程序校验，双保险。
- **备选方案**：仅靠 Prompt 约束长度（不稳定）——补充程序校验。

## 8. 弱匹配"角度切换"与防穿帮

- **决策**：在 Prompt 中内置匹配度判定与分支策略——强匹配引用量化数据（`achievements`）；弱匹配切换"学习/个人实践/底层逻辑"角度；显式约束"不得引入与用户经历无关的技术或工作经历"。生成的话术记录其 `source_experience_ids` 以支持可追溯校验。
- **理由**：满足 FR-008 / FR-009 / FR-013 / SC-002 / SC-003；`source_experience_ids` 支撑 SC-003 的"步骤上下文可追溯到真实经历"验收。
- **备选方案**：无（此为核心业务规则，必须实现）。

## 9. JD 解析与降级

- **决策**：`jd_analyzer` 用单模型结构化输出提取 `core_skills / duties / culture_values`；解析失败或 JD 缺失时置 `parse_status=failed` 并降级为"通用面试模式"（仅基于 Profile 生成），前端明确提示。
- **理由**：满足 FR-005 / FR-006；结构化输出稳定字段，降级保证可用性。
- **备选方案**：正则/规则抽取（对自由文本 JD 不稳健）——用单模型解析。

## 10. 测试策略

- **决策**：后端 pytest 分层——contract（接口契约）、integration（端到端生成流程，LLM 可打桩）、unit（Prompt 组装、长度/结构/编号步骤校验）；前端 Vitest + RTL 覆盖关键交互。LLM 调用在测试中以 mock/录制响应打桩，保证确定性。
- **理由**：满足验收标准的可验证性；对 LLM 打桩避免测试的非确定性与成本。
- **备选方案**：仅端到端真调用（慢、贵、不稳定）——仅在少量冒烟测试保留真调用选项。

## 11. 文档导入与解析（TXT / DOC / PDF）

- **决策**：后端 `document_parser` 服务支持三类格式：TXT（原生读取）、PDF（`pypdf` 提取文本层）、DOCX（`python-docx`）；旧版 `.doc` 通过可选的 LibreOffice headless 转换为 docx 后解析，若不可用则提示改为"附加原文"。提供两种用途：
  - **解析入库**：从文本抽取结构化"更新建议"（拟新增/修改的经历、技能、JD 字段），生成 `ProfileUpdateProposal`；写入个人知识库**前必须经用户确认**（差异确认界面，可逐项接受/忽略）。
  - **素材附加**：将文档原文保存为 `SourceDocument`（不强制结构化），在生成时作为参考上下文注入。
  扫描件（无文本层）无法提取时明确提示；OCR 不在本期范围。
- **理由**：满足 FR-020~FR-023；`pypdf` / `python-docx` 为纯 Python、轻量、离线可用，契合本地隐私原则（III）；"先建议后确认"契合宪法原则 I（防误覆盖）与 II（用户可控）。
- **备选方案**：`unstructured` / `textract`（能力全但依赖重、含二进制/系统依赖）——未选；云 OCR / 云解析（隐私风险 + 联网）——未选，与本地私有化冲突。

## 12. 悬浮实时辅助窗（Overlay）

- **决策**：以 Electron 独立 `BrowserWindow` 实现置顶悬浮窗——`frame:false`、`transparent:true`、`alwaysOnTop:true`、`skipTaskbar:true`。要点：
  - **无标题栏**：不设标题栏，悬浮窗**整体可拖拽**（通过 `-webkit-app-region: drag` 作用于非交互区域，或手动 `mousedown/mousemove` + `win.setPosition`），仅保留一个极小的关闭入口，最大化减少遮挡与存在感。
  - **透明度**：`win.setOpacity()`，设**可读性下限**（如 ≥ 0.35，低于阈值即钳制）。
  - **流式速率前置**：打字机速率作为**生成前的预设**（在生成工具栏选择），生成时即以该速率吐字；不放在悬浮窗内，保持悬浮窗简洁。
  - **自动缓慢滚动（提词器）**：生成中与生成后，回答以稳定的缓慢速度自动滚动（`requestAnimationFrame` 递增 `scrollTop`），使用户视线固定；提供暂停/恢复，用户滚轮交互时不被打断。
  - 呈现偏好（方式/透明度/位置/速率/自动滚动）持久化到 SQLite 的 `DisplaySettings`，下次沿用。
- **理由**：满足 FR-024~FR-028 与 SC-011/012/013；无标题栏 + 整体拖拽更贴近真实"面试小抄/提词器"的不打扰体验；自动滚动让用户朗读时视线稳定；速率前置符合"生成前设定"的使用习惯。生成内容经同一后端 SSE 流驱动主面板或悬浮窗，二者仅呈现层不同。
- **备选方案**：保留标题栏拖拽（更易发现但更占空间、更显眼）——按用户要求去除；浏览器画中画 / PWA 悬浮（无法真正跨应用置顶）——不满足；操作系统级 overlay（平台差异大）——未选。

## 13. 多轮对话与会话管理

- **决策**：引入 `ConversationSession` + `Message` 实体。一个 Session 代表一次独立面试准备对话（如"腾讯面试准备"），包含一组有序的时间戳消息。多轮追问走同一 Session，上下文以"最近 N 条消息 + 关键事实摘要"的滑动窗口机制管理：当消息量超出模型上下文窗口时，对早期消息自动摘要并保留"已讨论经历、已生成内容摘要、用户反馈要点"等关键事实，确保后续生成仍能锚定正确上下文。切换 Session 时前端切换视图并重加载对应消息历史。
- **理由**：满足 FR-029~FR-032 与 SC-014/015；滑动窗口 + 事实摘要比纯截断更稳健（不丢失关键信息），也无需引入 RAG 向量检索（对齐 RAG 延后的决策 §4）。
- **备选方案**：纯截断（简单但易丢失关键事实）——未选；全量持久化 + RAG 检索（引入 Pgvector，MVP 延后）——未选。

## 14. 语音输入扩展点（占位）

- **决策**：定义 `VoiceAdapter` 抽象——仅定义一个扩展注册协议（`name` + `type` 标识符 + `enabled` + `settings` JSON blob），不实现任何具体语音识别。UI 层预留麦克风按钮及"请先配置语音识别扩展"的禁用提示。后续由用户/社区按协议开发具体的语音识别插件（如 Web Speech API 封装、本地 Whisper 封装、云服务等）并注册到系统中。扩展发现机制：系统启动时扫描注册目录或用户手动配置扩展路径，加载已启用的适配器。
- **理由**：满足 FR-033/FR-034 与 SC-016；语音识别属复杂、依赖重的领域——自研不划算，扩展点+社区/第三方接入是务实的开放策略。协议足够简单（名字+类型+JSON 配置），降低适配器开发门槛。
- **备选方案**：内置 Web Speech API（跨平台不一致、离线不可用）——仅作为一种适配器留待实现；云服务直接集成（隐私风险、依赖网络）——不符合数据私有化原则 III。

## 15. 提示词模板可视化管理

- **决策**：在左侧导航栏新增"提示词管理"面板。模板以 `PromptTemplate` 实体持久化到 SQLite——含 `scope`（self_intro|scenario）、`structure_rules`、`style_rules`、`is_builtin`。内置模板 `is_builtin=true` 不可删除；用户编辑内置模板时自动"另存为"（copy-on-edit），生成一个用户自定义副本。生成时用户从模板列表选择一个当前活跃模板，切换即时生效（不重置会话上下文）。模板支持导出/导入为 JSON 文件，便于备份与社区共享。
- **理由**：满足 FR-035~FR-039 与 SC-017；可视化管理降低普通用户的 Prompt 工程门槛（无需编辑代码/原始 Prompt）；模板切换是实际中高频操作（不同公司/岗位需要不同风格），独立于会话存在。
- **备选方案**：直接编辑原始 Prompt（面向开发者友好、对普通用户不友善）——用结构化表单代替；GPTs 式纯自然语言描述（不可控、不满足硬规则原则 II）——保留结构化规则。

## 16. 对话优先架构与斜杠命令设计

- **决策**：删除独立的"自我介绍页"和"场景题页"，二者融入对话流成为斜杠命令。以**一个会话 = 一个岗位的完整面试准备**为模型——输入 `/intro [要求]` 生成自我介绍、`/scenario <问题>` 生成场景题回答、`/followup` 让 AI 模拟追问。所有输出以对话气泡展示在同一会话流中。输入 `/` 触发命令补全下拉。后端 conversation_service 根据 command 字段路由到对应生成服务。
- **理由**：一个岗位的全部准备活动共享同一上下文；斜杠命令只需记住 3 个，无需多页面跳跃；与语音输入（VoiceAdapter）天然兼容——口述 /intro 即触发生成。
- **备选方案**：独立页面+按钮（切换丢失上下文）——未选。
