# 核心技术解析（AI应用开发视角）

## 1. RAG知识库注入管线

**做了什么**：每次LLM调用前，自动从SQLite加载6张表的数据，按结构化字段+附件原文+JD关键词三类源，通过模板系统格式化为System Prompt。不是简单的f-string拼接。

**怎么做的**：

```
build_profile_data_for_prompt(db)
  ├── profile → name/phone/email
  ├── internships → company/position/achievements (JSON字段)
  ├── projects → tech_stack/challenge/solution/result (JSON字段)
  ├── skills → category/name/proficiency
  ├── profile_docs → extracted_text (SourceDocument表, scope=profile, usage=attach, 截断3000字)
  └── jd_docs → extracted_text (SourceDocument表, scope=jd, usage=attach, 截断3000字)
```

每个数据源有独立的截断策略。`profile_docs`和`jd_docs`是用户上传的原始文档被提取后的纯文本(`pypdf`/`python-docx`提取)，保存在`extracted_text`字段（上限50000字），注入Prompt时再截到3000字。这样既保留了完整文档用于管理，又控制了Token消耗。

**为什么比直接f-string好**：每个数据源有独立的元信息标签（`【附加个人素材-xxx.pdf】`），LLM能区分信息来源。结构化字段（JSON）先被格式化为自然语言摘要，减少Token浪费。

## 2. 意图分类 + Prompt动态路由

**做了什么**：用户不用打`/`前缀。输入"帮我写一段自我介绍"和"写一个快排"走完全不同的System Prompt——自动识别。

**怎么做的**：

```python
def classify_interview_intent(content):
    # 关键词打分法（非LLM，零延迟）
    intro_score = sum(1 for kw in _INTRO_KEYWORDS if kw in content)
    tech_score  = sum(1 for kw in _TECH_KEYWORDS if kw in content)
    scenario_score = sum(1 for kw in _SCENARIO_KEYWORDS if kw in content)

    if tech_score > intro_score and tech_score > scenario_score: return "/technical"
    if scenario_score > intro_score and scenario_score >= tech_score:    return "/scenario"
    return "/intro"  # 默认
```

三个category对应三套独立的System Prompt模板，每套都有独立的`TemplateDefault`（用户可在模板管理页设置为默认）。分类不需要额外LLM调用——这是关键，否则每次对话前要额外消耗一次API调用做分类，增加了延迟和成本。

**面试模式 vs 普通模式的双路由**：

```
用户消息 → classify_message()
  ├── 含面试关键词 → interview模式 → pro模型 + 知识库注入 + 模板
  └── 非面试 → normal模式 → fast模型 + 简洁回答
```

## 3. 多Provider LLM抽象层

**做了什么**：一套代码支持DeepSeek/GPT/Claude三个Provider，运行时热切换，不需要重启。

**怎么做的**：

```python
class LLMClient:
    def configure(self, api_key, base_url, model):
        self.api_key = api_key
        self.base_url = base_url
        self.model = model
        self._client = AsyncOpenAI(api_key=api_key, base_url=base_url)

    async def stream(self, messages, model=None):
        resp = await self._client.chat.completions.create(model=model or self.model, stream=True)
        async for chunk in resp:
            delta = chunk.choices[0].delta
            reasoning = getattr(delta, "reasoning_content", None)  # DeepSeek专有
            if reasoning: yield {"type": "thinking", "content": reasoning}
            if delta.content: yield {"type": "token", "content": delta.content}
```

关键点：
- OpenAI兼容接口统一了三个Provider的调用方式
- `getattr(delta, "reasoning_content", None)` — DeepSeek专有字段，非reasoning模型(如deepseek-chat)没有这个属性，`getattr`安全fallback
- `configure()`方法允许UI修改设置后实时生效，每次`POST /api/generate`前从数据库读取活跃ApiKey并调用`configure()`
- `asyncio.Semaphore(3)`全局限流——最多3个并发LLM调用，防额度耗尽
- 流式返回从`AsyncIterator[str]`升级为`AsyncIterator[dict]`，前端用`event: thinking` vs `event: token`区分思考链和回答

**ApiKey管理**：`api_keys`表存多个Key，每个Key有独立的`provider`/`api_key`/`model`/`is_active`字段。切换Key时调对应Provider的API验证有效性并拉取模型列表。这个设计支持用户同时拥有DeepSeek和GPT的Key，按需切换。

## 4. SSE流式 + Markdown实时渲染

**做了什么**：AI回答逐字出现在界面上，同时Markdown格式（标题、加粗、代码块、数学公式）立刻生效——不会出现"半成品`**data`闪烁再消失"。

**怎么做的**：

```
后端 FastAPI AsyncGenerator → EventSourceResponse → SSE event stream
前端 fetch ReadableStream → 按行解析SSE帧 → rAF节流setState → MarkdownRenderer
```

**MarkdownRenderer的流式策略**：流式内容按最后一个`\n`拆成"已完成行"和"当前行"。已完成行通ReactMarkdown完整渲染；当前行用纯文本`white-space:pre-wrap`+闪烁光标。这解决了不完整Markdown(如`**粗体`)被解析器显示为源码的问题。

**性能优化**：`requestAnimationFrame`节流——每个SSE token(~16ms一个)到达后不立即`setState`，而是等rAF统一flush，避免每帧多次重渲染ReactMarkdown。

## 5. 思考链可视化（Chain-of-Thought）

**做了什么**：DeepSeek V4 Pro的`reasoning_content`被单独提取，在UI中显示为可折叠的灰色思考面板——对标DeepSeek官网体验。

**怎么做的**：

```
Delta.reasoning_content → SSE event:thinking → 前端累积字符串 → 思考面板(可折叠, 字数统计)
Delta.content            → SSE event:token    → 前端累积字符串 → Markdown渲染区域
```

两个流式通道独立传输。思考过程在发送回答前就已经开始显示——用户看到AI"正在思考"，而不是干等几十秒后直接弹出答案。思考内容在流式完成后默认折叠，用户可点击展开查看。数据库`messages`表的`thinking`列会持久化思考内容，历史消息再次打开时依然可见。

## 6. 音频采集（AudioWorklet直连讯飞）

**做了什么**：用户说话实时转文字，填入输入框。纯前端方案，不经过Python后端中转。

**怎么做的**：

```
麦克风 → AudioContext(16000Hz) → AudioWorklet(PCM采集) → 浏览器WebSocket → 讯飞服务器 → 文字
```

**遇到的三个关键坑**：

**坑1：Worklet不触发process()**。`AudioWorklet`是现代浏览器采集音频的标准方式，但有一个隐蔽行为——**Worklet必须有输出连接才会触发`process()`**。解决方案：加一个`GainNode(0)`连接到`audioCtx.destination`强制激活音频图，同时gain为0避免回授。

**坑2：死锁——音频不发，服务不等**。最初代码在收到服务端首个响应前不发送音频数据（`if (!ready) return`）。但讯飞IAT API需要先收到音频才开始响应——形成"你不给我数据我不理你，你不理我我不给你数据"的死锁。修复：直接发送音频，不等服务端ready。

**坑3：原始PCM二进制被拒**。讯飞IAT WebSocket API的文档暗示可以直接发送原始二进制PCM（`encoding: "raw"`），但实际服务器拒绝并返回`"request data must be valid json string"`。修复：将PCM数据用JavaScript的`btoa()`编码为Base64，包装在JSON帧中发送：
```javascript
ws.send(JSON.stringify({
  data: { status: 1, format: "audio/L16;rate=16000", encoding: "raw", audio: b64 }
}));
```

**为什么不用后端中转**：纯前端方案避免了音频数据在网络上的往返延迟。后端仅提供讯飞WebSocket的HMAC-SHA256签名URL（`/api/settings/voice/auth-url`），浏览器拿到签名URL后直连讯飞服务器。

## 7. 提示词模板系统

**架构设计**：三种scope（自我介绍/场景题/技术题），每种scope有一个内置模板+用户自定义模板。模板设为**全局**（`profile_id=0`），切换简历不影响模板配置。`TemplateDefault`表记录每个scope当前使用的默认模板ID（仍按profile绑定——每份简历可以选不同默认模板，但模板池共享）。

不是简单的把用户输入的JSON塞进Prompt——`_validate_template_rules()`在校验时会检测7种Prompt注入模式（如"ignore all previous instructions"），防止恶意模板劫持LLM行为。所有字符串值上限500字符，JSON key必须是字典类型。内置模板不可编辑，编辑时自动"复制副本"（Copy-on-Edit模式）。

```python
_template_scope_map = {
    "/intro": "self_intro",
    "/scenario": "scenario", 
    "/technical": "technical"
}
# 对话时按分类加载对应scope的默认模板
template_rules = _load_template_for_scope(db, scope)
```

## 8. 全局 ApiKey 管理系统

**架构设计**：ApiKey 与模板一样改为全局管理（`profile_id=0`），切换简历不影响已配置的Key。

**锁机制**：`activate_apikey()`激活前先全量`is_active=False`，保证同时只有一个活跃Key。`get_active_apikey()`发现多个`is_active=True`时自动修复（历史遗留）。

**去重**：添加Key时检查Key值和名称是否已存在，重复则返回409错误。

**强制验证**：添加Key时调用Provider API验证有效性，无效Key拒绝保存。切换Key时重新验证，已失效Key返回401阻止切换（前端提示删除或换Key）。

**错误提示**：所有API错误（重复/无效/失效）通过`ApiError`向上传播，前端`onError`回调直接展示后端返回的具体原因，不再用泛化的"添加失败"。

## 9. LLM 未配置拦截体系

**做了什么**：所有依赖LLM的功能在操作前统一检查ApiKey是否已配置。未配置时**连文件选择器都不弹出**，直接弹出引导弹窗。

**拦截点**（8处全覆盖）：
- 对话发送（ConversationPage）
- 简历文档上传/解析/重新解析（ProfilePage + DocumentImport）
- JD文档上传/分析（JDPage + DocumentImport）
- 素材上传（ProfilePage/JDPage + DocumentImport + KnowledgeSelector内联上传）
- 模拟面试开始（InterviewPage）
- 简历评审开始（ReviewPage）

**引导弹窗**：点击"前往设置"→ 通过`CustomEvent("navigate")`跳转设置页 → 对应区域（LLM Key区/语音区）**金色光晕闪烁2.5秒**自动消失。语音区还会自动展开折叠面板。

**实现**：共享组件`ApiKeyRequiredDialog` + 共享hook`useLLMStatus`（查询`GET /api/settings/llm/status`）。DocumentImport的onClick中拦截`fileRef.click()`，拖拽时拦截`handleFile`。
