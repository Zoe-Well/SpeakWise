# SpeakWise 面试问答

> 更新时间：2026-07-27

## Q1：这个项目算 Agent 还是普通聊天应用？

它更准确地说是一个**受控编排的面试 Copilot**。代码负责意图路由、上下文、状态、记忆和安全边界，LLM 负责生成内容。目前没有 ReAct、自主工具调用或多 Agent 协作。

## Q2：为什么没有使用传统 RAG？

用户数据主要是结构化简历、少量 JD 和附件，规模较小。项目直接从 SQLite 加载当前活跃数据，通过 `ContextBuilder` 按类别预算注入 Prompt，不需要 Embedding 和向量检索。

优点是简单、稳定、可解释；缺点是资料规模变大后，相关信息选择能力不如向量检索。

## Q3：Prompt 是怎么设计的？

Prompt 分为三层：

1. System Message 定义角色、事实约束和行为边界；
2. 自我介绍、STAR 场景题、技术题使用独立任务模板；
3. User Message 放简历、JD、附件、当前问题和用户格式偏好。

模板规则经过 JSON、长度和部分注入关键词校验。用户内容仍可能存在 Prompt Injection 风险，企业化时应进一步使用严格 Schema 和内容隔离。

## Q4：如何控制上下文长度？

项目使用近似字符预算，不绑定特定模型 tokenizer：

- 简历：6,000；
- JD：2,500；
- 个人附件：合计 5,000；
- JD 附件：合计 3,000；
- 旧对话摘要：2,000；
- 最近消息：8 条、合计 6,000。

多个附件共享类别预算，不再每个附件各截取固定长度。

## Q5：多轮记忆如何实现？

最近 8 条消息保留原文。更早的消息由快速模型整理成滚动摘要，保存到 `ConversationSession.memory_summary`，并用 `summary_up_to_message_id` 记录摘要位置。

结构化简历、项目、技能、JD 和附件属于长期知识记忆；系统不会未经用户确认就把聊天内容写回简历。

## Q6：模型和意图如何路由？

面试模式使用“显式 Slash 命令 → 高置信加权规则 → 短追问继承 → 快速模型分类”的混合路由，识别自我介绍、场景题、技术题和追问。普通模式先判断是否与面试相关：相关问题使用主模型，其他问题使用与当前 Provider 兼容的快速模型。

明确问题由规则直接路由，不增加调用；只有低置信或冲突输入才使用快速模型。分类失败或置信度不足时回到通用面试回答。

## Q7：如何保证流式生成的可靠性？

后端通过 SSE 分离 `thinking` 和 `token`。统一 `GenerationGuard` 对各生成入口提供：

- 会话归属和模式校验；
- 同一任务并发互斥；
- 30 秒窗口频率限制；
- 服务端详细日志与前端错误脱敏。

LLM semaphore 覆盖完整响应流，而不是只限制请求创建阶段。

## Q8：为什么直接使用 SDK，而不是 LangChain？

项目需要直接读取 DeepSeek 的 `reasoning_content`、自定义 SSE 事件，并精确控制 Prompt 和上下文预算。直接使用 OpenAI 兼容 SDK 更轻量，也更容易调试。

如果未来引入复杂工具调用、向量检索或多 Agent 协作，再评估 LangGraph 等编排框架会更合适。

## Q9：这次架构优化解决了什么问题？

- 统一会话默认模式并支持模式切换；
- 明确 JD 以全局活跃记录为唯一来源；
- 消除附件和历史重复注入；
- 引入分区上下文预算和滚动摘要；
- 统一生成入口的并发、限流、归属校验和错误处理；
- 增加上下文、记忆、迁移、门禁和流式并发测试。

## Q10：后续最值得做什么？

如果资料规模继续增长，优先增加附件切块、Embedding、Top-K 检索和来源引用。如果系统转为多人 SaaS，还需要把进程内门禁迁移到 Redis，并把全局可变 LLM 客户端改为请求级客户端。
